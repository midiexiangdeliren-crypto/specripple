# 需求变更驱动的多工件自动对齐 —— 实现方式规划

基于《深入理解 AI Agent》教材方法论，参考 superpowers 与 GitHub Spec Kit　　2026 年 9 月 17 日

本规划是《研究方案》M1—M7 的工程落地版，回答"用什么方式实现"。三份参考的分工：李博杰《深入理解 AI Agent：设计原理与工程实践》（本机 ai-agent-book-main，10 章正文 + 109 实验）提供方法论底座——Agent = Model + Harness，第 2 章上下文工程、第 3 章记忆与知识库、第 5 章 Coding Agent、第 7 章评估直接支撑我们的仓库、检索与评测设计；GitHub Spec Kit 提供工件模板层与对照基线——其单向生成流水线（constitution → specify → clarify → plan → tasks → analyze → implement → converge）调研确认存在三大缺口：没有"改 spec 后自动传播到 plan/tasks/代码"的变更传播、冲突检出只有 LLM 只读报告而无确定性检测层、analyze 只在实现前跑一次而非传播后增量复检——这正是本课题的创新空间；obra/superpowers 提供流程纪律层——技能触发式加载、计划任务颗粒化、子代理两段评审、完成前强制复验。一句话定位：我们要造的是 Spec Kit 之后的"对齐层（alignment layer）"，模板兼容 Spec Kit，行为纪律借鉴 superpowers，传播闭环是自己的贡献。

## 一、总体路线选择

推荐路线：自研轻量编排核心（Python）+ 兼容 Spec Kit 工件格式。理由有三。其一，fork Spec Kit 源码不可取：它的能力分散在提示词、模板与 CLI 中，变更传播塞进去后科研贡献难以剥离，且上游迭代快、版本漂移难维护。其二，兼容其模板收益明确：实验可以直接用 /specify、/plan、/tasks 命令产出初始工件，保证"Spec Kit 基线"与"本系统"在同一工件上对照，公平且省事。其三，工作量可控：核心 Python 包约 3—5 千行，无前端，符合本科毕设预算。

已否决方案（开题答辩可用作论证）：纯自研格式——自由度高但失去现成对照基线，且评审会问"为什么不兼容现有 SDD 工具"；直接改造 Spec Kit 源码——见理由一。

技术栈：

| 项 | 选择 | 说明 |
| --- | --- | --- |
| 语言与环境 | Python 3.11+，uv 管理依赖 | 本机 Windows，注意统一 UTF-8（脚本内显式 encoding，必要时 PYTHONIOENCODING=utf-8，防 GBK 乱码） |
| 数据模型 | pydantic v2 | 条目 schema、变更提案、冲突报告的强校验 |
| 工件存储 | 文件系统 + Git | Markdown 正文 + YAML frontmatter；最小 diff、可回滚、可审计（教材第 3 章"知识更新当 PR"） |
| 检索 | rank_bm25 起步，可选 bge-small 稠密 + RRF | 先 lexical 通道跑通，稠密与重排序按需加 |
| LLM 接入 | OpenAI 兼容接口 | DeepSeek / GLM / Kimi 任一（教材 README 有 key 指南）；规则层零 token |
| 交互 | Typer CLI + rich 终端 | 对话消解在终端完成；不做 Web UI（工作量陷阱，属教材反面模式） |
| 测试与评测 | pytest + evals/ 内联脚本 | 评测集与单测分开管理 |

## 三、系统模块实现方式（对应研究方案 M1—M7）

### M-A 条目化工件仓库

做法：把 Spec Kit 产出的文档解析为条目。每条目一个文件，YAML frontmatter 含 id（REQ-xxx / PLAN-xxx / TASK-xxx / CON-xxx）、type、status、depends_on[]、links[]（区分自动/人工）、source、content_hash。正文采用 EARS 式半形式化模板加 Given/When/Then 验收（清单 16 的结论支持此选择），兼容 Spec Kit spec-template 的 P1—P3 用户故事、FR-xxx 编号与 [NEEDS CLARIFICATION] 标记——解析时把该标记转为条目的 pending_clarification 状态，消解后原子写回。上下文加载采用三层渐进式披露（教材第 3 章 OpenViking 文件系统范式 + 第 2 章 Agent Skills 机制）：index.json（每条目约 100 字符摘要）常驻系统上下文；正文按需加载；关联全文再按需。索引是可重建的派生物，任何时候可从条目文件全量再生成。Git 管理保证每次传播都是最小 diff、可回滚。

来自哪里：教材第 2/3 章（渐进披露、分层加载、PR 式更新）；Spec Kit 模板（兼容对象）；清单 16（模板选择依据）。

### M-B 链接三通道

通道一（确定性）：frontmatter 显式引用 + Spec Kit tasks 的用户故事分组天然构成链接，零成本。通道二（检索）：BM25 起步，分块时加来源前缀（教材第 3 章"上下文感知检索"，检索失败率降 49% 的技巧），稠密向量与 RRF 融合按需引入。通道三（LLM）：TraceLLM 式提示（清单 07），只对前两通道低置信的区间运行以省成本。融合层做加权投票加阈值，输出带置信度的链接集。评估用 recall@k / MRR，起步人工标注 30—50 条链接即可。

### M-C 影响分析双通道

需求通道：在链接图上从变更条目 BFS 得到传播候选，再用 LLM 补充"语义受影响但缺链接"的条目（补的就是三通道漏掉的）。代码通道：静态 import/调用关系做粗粒度映射，加 git 共变更历史作为先验（清单 03 Trustrace 思想；spec-first 工作流初期无历史时冷启动降级为纯静态）。输出影响集，每项附"为何受影响"的证据链——这条证据链同时服务消解对话和复检器，是 debug 与论文分析的关键中间产物。

### M-D 传播策略 L0—L3

分级执行：L0 常量/文本级变更走模板替换（确定性工作流）；L1 单条目措辞变更走条目重写（工作流）；L2 跨条目结构调整走 LLM 增量修订（自主循环）；L3 目标级或宪法冲突先进消解对话，再决定全量重生成或拒绝。这是教材第 1 章的混合编排结论：确定性部分用工作流，需判断的部分用自主循环。每次传播产出"变更提案"结构化对象：根因、归属组件、预期修复、可能受损项、各自的验证用例（教材第 9 章"可证伪变更契约"）——提案经复检器通过才落盘。成本与稳定性靠 KV Cache 三铁律（教材第 2 章）：系统提示与工具定义字节级不变、动态信息只追加末尾、标准消息格式；并用"状态栏"模式把待传播条目数、冲突数、已传播项作为显式结论注入上下文末尾、由代码维护（教材实验 2-8/2-9：迭代次数 21→15）。

### M-E 双层冲突检出

规则层先跑（零 token，教材第 5 章"约束优先于指导"——能写成 Linter 的绝不写提示词）：引用完整性（depends_on/links 指向存在的 id）、术语表一致性、TODO 与未决标记残留、EARS 结构合法性、状态机非法迁移（如已完成任务被新变更波及但未重开）。规则集源自 Requirements Smells（清单 09）并扩展到工件间一致性。LLM 层后跑：参照 Spec Kit /analyze 的六类检查（重复、歧义、欠规范、宪法对齐、覆盖缺口、不一致）输出 CRITICAL—LOW 分级，但有两处关键差异——我们的 LLM 层在每次传播后增量运行（Spec Kit 只跑一次），且对可自动修复项直接产出传播提案而不只是报告。双控原则：LLM 自查结果必须过规则层结构校验，不采信模型自报（教材第 5 章"业务规则三重保障"）。

### M-F 对话消解器

交互协议直接沿用 Spec Kit /clarify 的成熟形态：一次一题、每题 2—4 个选项附推荐项、答案原子写回条目并同步融入正文（替换而非叠加）。触发逻辑：M-E 的 CRITICAL/HIGH 冲突先自动分类为"可裁决 / 需用户裁决 / 需补充信息"，只把后两类抛给用户——这与 /clarify 在起点澄清不同，我们澄清的对象是"变更与既有工件集的冲突"（与清单 13 CLARITI 的差异化叙事一致）。每次消解落盘一条 rationale 条目（对应清单 01 的论证链接），供复检器与论文分析使用。多轮对话遵守 KV 三铁律控成本；历史过长时"隔离优于压缩"（教材第 2 章）——派子代理消化历史只回结论。

### M-G 复检器

提议者—审核者结构（教材第 1、10 章）：传播提案由独立上下文的审核者验证，只看结构化产物、不看生成过程，模型不能批准自己的"完成"；借鉴 superpowers 的两段评审（先 spec 合规、再代码质量）与"证据先于宣告"（verification-before-completion）纪律。验证内容用 SWE-bench 语义搬到工件层：FAIL_TO_PASS（变更应当修复的 GWT 断言）+ PASS_TO_PASS（保留集断言不得破坏），再加上"边界集回归"——验证无关工件确实未被改动（教材第 1 章边界集思想）。测试通过率不等于需求满足（清单 18），所以复检以 GWT 断言级检查为主、测试通过为辅。

## 四、评测方案（教材第 7 章方法论落地）

评估环境五要素套用：数据集 = evals/ 变更用例集；可重置环境状态 = git tag 回放；双侧原子工具接口 = 传播器与复检器的 CLI 子命令；Rubric = 各指标的判定细则；执行协议 = 轮数上限与终止条件。变更用例集三种构造方式并行：参数化模板合成（控制变更类型、规模、冲突密度，兼防泄漏）；回放真实仓库历史提交并用失败归因沉淀回归对；轨迹前缀回归——冻结出错前状态，把"可接受动作集合"作为答案而非唯一标准答案，成本低且能隔离单点策略。

指标体系（对应研究方案汇总表）：

| 指标 | 口径 | 教材依据 |
| --- | --- | --- |
| CRR 一致性保持率 | 受影响工件全部对齐且保留集无一票否决项，按 Pass^k 连续口径 | 第 7 章 Pass@k 与 Pass^k 之辨 |
| 漏检代价加权分 | 按冲突严重级加权求和 | 第 7 章 rubric 按重要性加权 |
| 误拦截率 | 规则层+LLM 层拦截中判定为误报的比例 | 第 7 章过程级四层校验 |
| Ask-F1 | 消解器提问质量，用模拟用户评（渐进式信息透露 + 事实锚定，τ²-bench 式） | 第 7 章模拟用户设计 |
| 成本 | 调用数、token、端到端时延 | 第 7 章评估驱动选型 |

统计与消融：配对设计（同任务同种子）+ 每配置 3—5 种子 + bootstrap 置信区间；预期差异小于 3 个百分点时先扩样本再谈结论。消融三组：三通道去一、双层去一层、L2 提案有契约 vs 无契约；另做模型替换实验（固定 Harness 换模型）区分模型瓶颈与 Harness 瓶颈——这是论文实验章的骨架。LLM-as-judge 遵守四准则（专家指导、覆盖陷阱项、加权 + 一票否决项如幻觉归零、各档自包含可验证），用多源异构评委防同源互骗，交换顺序评两次防位置偏差。

## 五、里程碑 M1 落地步骤（建议 4—6 周，每步自带验证）

| 步 | 内容 | 产物 | 验证方式 |
| --- | --- | --- | --- |
| 1 | 环境就绪（uv、key、Git），跑通 Spec Kit 小项目全流程 | spec-kit-baseline/ 工件样例 | 全流程产物齐全，人工走查 |
| 2 | 条目 schema v0 + Spec Kit 模板转换器 | repo/ 模块 | 单元测试 + 样例项目 100% 条目化、索引可重建 |
| 3 | 链接通道 v0（确定性 + BM25） | links/ 模块 | 30—50 条人工标注，recall@k 报告 |
| 4 | 变更用例 v0（5—10 个人工金标准传播 diff） | evals/ | 金标准双人复核入库 |
| 5 | 最小传播闭环（L1 级：单条目措辞变更 → tasks 重写 → 复检） | propagate/ + verify/ 骨架 | 首次 CRR 测量并有数字 |
| 6 | 判定点：L2 全量重生成 vs 增量传播是否可区分（对应研究方案 M2 末降级判断） | 1 页实验纪要 | 数据支撑的 go / 降级决策，导师过目 |

每步遵循 superpowers 纪律：任务切到 2—5 分钟颗粒、每任务先定义验证、完成前"证据先于宣告"。第 6 步是整个课题的第一个科学判定点，务必留下数据。
