# specripple 实际开发价值与差距复评

评估日期：2026-09-18。对象为实际开发方向，不以论文创新性或实验章节完整度评价产品。

## 1. 结论

建议继续投入，但应调整下一阶段重点：把 specripple 做成 AI 编程过程中可审计的变更影响与验收工具，而不是继续扩大“所有工件自动保持一致”的承诺。

当前已有可运行的确定性 CLI、宿主技能和小规模真实联动案例。它已经越过纯方案阶段，证明了“在选定示例上可以串起流程”。但尚未证明“比宿主 Agent 加一段同步提示更少遗漏、更省人工，且能在持续变更的真实仓库中稳定工作”。

工程可行性已有证据，独立产品价值仍待验证。现阶段适合作为面向采用规格文档的个人开发者、小团队的开源工具；没有足够证据支持独立平台或商业产品判断。

建议定位：**面向既有代码仓库，在需求变化后列出影响依据、遗漏风险和可执行验收结果的轻量对齐工具。**

## 3. 方向价值的重新判断

### 有价值的部分

长期维护的项目中，规格、计划、任务、代码、测试和决策记录会随变更出现偏差。宿主 Agent 可以编辑这些文件，但开发者仍然需要判断它是否找到所有相关位置、是否漏改、是否以修改测试掩盖回归。显式依赖图、可复查证据和机器可执行检查，可以降低这种判断成本。

把 LLM 执行交给宿主，自己维护小型 CLI，是合理的工程分工。它减少模型接口、会话系统与编辑工具的维护成本；`command` 检查器也使验证从纯文档文本检查走到了实际代码行为。

最适合的早期使用者，是已经维护规格与验收测试、且经常进行跨文件需求调整的开发者。短期脚本、很少保留规格的小项目，可能无法从手工维护条目和链接中获得足够收益。

### 需要修正的差异化假设

最初规划将 Spec Kit 概括为单向生成、缺少实现后闭环。当前官方文档已经包含：

- Living Spec：修改 spec，更新 plan/tasks，analyze，再 implement/converge。
- Flow-Back Spec：允许从代码或其他工件开始，根据新发现重新对齐工件。
- implement/converge 循环：发现剩余缺口并补任务。

OpenSpec 同样明确描述需求修改、实现后 `/opsx:verify`、代码与规格偏差的协调以及归档同步。不能再把“有变更闭环”本身视为独有能力；这些资料也没有证明它们已解决全部确定性追踪问题。

真正值得验证的差异是：**同一模型、同一任务下，specripple 是否减少漏改，说明影响依据，并对错误完成给出更可靠的阻断。** 三份技能、BFS 和基础文本检查本身容易复现，持续积累的兼容能力、可靠性与真实失败案例才可能建立优势。

## 4. 实现与规划对照

三份规划是演进关系，应以最新《开发执行计划》的 MVP 为当前交付基线。早期自研编排、直接接 LLM、完整研究指标不应全部算作欠账。

| 能力 | 目前实现 | 相对计划与实际使用的差距 |
| --- | --- | --- |
| 条目仓库与 index | YAML/Markdown、模型校验、重复 ID 检查、可重建索引 | 核心 MVP 已有；缺来源映射、内容指纹和变更前基线 |
| impact | 显式 links 出边和反向 depends_on 的 BFS，含到达证据链 | 没有语义补链、代码映射、Git 变更识别；输出的 path 是 ID 链，未提供计划承诺的工件文件路径 |
| detect | 六类确定性规则框架 | 部分规则明显弱于表述；不能据此证明语义一致或需求覆盖完整 |
| verify | 两组断言，五种检查器，包含 command | 比原四检查器范围前进了一步；JSON 失败退出码有缺陷，缺覆盖与基线保护 |
| 传播与 L0-L3 | 宿主按技能编辑与判断 | 是软性流程指令；无机器校验的传播清单、提案契约或范围约束 |
| 冲突消解与 rationale | 对话协议、RAT 条目，在本地案例中已使用 | 无专用 log 命令或结构化裁决验证；当前依赖宿主执行 |
| 宿主安装 | Codex/Claude 的 init、dry-run、remove；通用技能可用于 DSH | Claude 真机验证按用户决策暂缓；生成指令仍有旧命令残留 |
| Spec Kit 导入 | 故事转 REQ、任务转 TASK、计划与宪法转单条目，有黄金快照 | 是一次性迁移；非空仓库拒绝导入，无持续同步/回写；官方格式存在兼容遗漏 |
| 真实端到端 | 小型登录场景及文档传播、交互消解案例 | 未覆盖中等规模、多次变更、缺链、多人修改、多种模型 |
| 分发与复现 | GitHub 安装说明、双语 README、79 个测试 | 未见三平台 CI、LICENSE、公开自动化 Agent 评测；手工实测目录在仓库之外 |
| MCP/BM25/报表 | 未实现 | 执行计划明确后置，不构成当前 MVP 偷工减料，也不是现在最急的工作 |

“D1-D14 全部完成”的回填过于笼统：同文又注明 D12 暂缓，官方模板兼容也没有达到宣称的完整验收。更准确的状态是：**主要 MVP 命令已交付，部分验收与产品可靠性未闭合。** 暂缓 Claude 和不发 PyPI 都是已有用户决策，不建议为了看起来完成而重启。

## 5. 已核实的主要问题

### 5.1 高优先级：JSON 验收失败仍返回成功

位置：`align-kit/src/specripple/cli.py:128`。

`verify --json` 输出报告后直接 return，跳过后面的失败退出逻辑。本次向真实验证器注入一条缺失文件断言：普通模式退出 1，JSON 模式报告 failed=1 却退出 0。若脚本或 CI 仅依赖退出码，会将失败当作成功。这直接违反执行计划中“任何断言失败都非零退出”的约定。

### 5.2 高优先级：Spec Kit 兼容入口与未决项存在缺口

位置：`speckit_import.py:19`、`detect.py:12`、`tests/fixtures/speckit-sample/spec.md`。

- 官方当前模板使用 `**Acceptance Scenarios**:`；转换器只规范化 Markdown 标题形式，测试夹具采用的是 `#### Acceptance Scenarios`。本次对官方格式片段运行解析，确认不会生成 `## Acceptance`。
- 官方模板使用 `[NEEDS CLARIFICATION: ...]`；D5 仅匹配没有冒号与内容的 `[NEEDS CLARIFICATION]`。本次对带内容标记运行 detect，未检出。
- 有黄金快照并不意味着锁定了官方模板版本；未见上游版本/提交与来源的锁定信息。

这会造成正常导入被报结构问题，而真实未决问题被漏过。

### 5.3 高优先级：影响集的覆盖上限取决于人工链接

位置：`impact.py:13`、`speckit_import.py:194`、`speckit_import.py:199`。

影响分析只沿已存在的边遍历；没有链接的语义相关条目、代码文件和测试不会自动进入结果。导入器把 PLAN/CON 写成无依赖、无链接条目，规格概览中的 FR 也没有单独关联到故事。

本次对黄金导入结果执行 `compute_impact(..., 'REQ-002')`，只得到 TASK-002 和 TASK-003，未包含 PLAN、规格概览或代码。并非每次修改都必须改这些工件，但目前没有证据能判定它们“已审查且无需变更”；图上不可达被混同成了不受影响。

应将影响集表达为有依据的候选集，并明确未覆盖区域。引入代码/测试文件映射、遗漏检查，比直接上向量检索更贴近当前问题。

### 5.4 高优先级：绿色验收不代表基线被保持

位置：`verify.py:55`、`verify.py:120`、`skills/aligning-changes/SKILL.md:32`。

- FAIL_TO_PASS 和 PASS_TO_PASS 当前只是两个同样执行的分组，没有读取修改前状态，不验证前者真的由失败转成功、后者原本通过且保持通过。
- 空配置 `{}` 被解析为两组空断言，结果 total=0、failed=0；普通 CLI 会报告 PASS。
- 分组名拼错也可能被当作缺失组静默忽略。
- 同一个宿主可以修改需求、代码、测试与 assertions.yaml；工具没有检查保留断言被删除或削弱。

允许因需求变化而调整测试是必要的，但调整理由和保留集应该可追溯。这里缺少约束，不代表已有实测一定通过作弊完成。当前证据能证明“当前断言通过”，不能证明“完整需求被满足且旧行为未被意外破坏”。

### 5.5 中优先级：部分规则与机器门禁语义尚不充分

位置：`detect.py:13`、`detect.py:66`、`cli.py:102`。

- D4 只要求出现 Given/When/Then 中任一英文单词。本次 `## Acceptance` 加一个 `Given` 就得到零问题；没有真正校验完整 GWT，也没有 EARS 校验。
- D3 判断当前 done 依赖 active/draft，不能判断“上游后来被重新打开”。真实团队经常让需求保持 active、实现任务标记 done，需要先明确状态含义，否则有误报风险。
- detect 对 CRITICAL/HIGH 也退出 0，本次使用原有夹具确认。这与当前测试约定一致，不应冒称为意外回归；但作为 CI 门禁，需要增加明确的失败阈值或 check 命令。
- pending_clarification 没有进入状态枚举，当前实现采用正文标记替代，与计划描述应统一。

### 5.6 中优先级：安装入口与长期维护体验

位置：`skills/aligning-changes/SKILL.md:13`、`init_host.py:21`。

技能还写着 `uvx align` / `uv run align`，生成的 AGENTS 块写 `uvx specripple`，与已决定“不发 PyPI，走 Git 安装”的路径不一致。熟悉本地仓库的 Agent 可能自行纠正，新用户环境容易卡住。

导入器只接受同目录的 spec/plan/tasks/constitution，不能直接发现完整 Spec Kit 项目的多 feature 与共享 constitution 布局；不支持重新导入和稳定来源映射。长期使用需要明确源文档和 artifacts 谁是唯一事实来源，避免维护两套文档造成新的偏差。

## 6. 下一阶段建议

### 第一阶段：修补当前承诺，发布维护版本

建议范围：JSON 失败退出码、空/错误配置策略、官方模板与澄清标记兼容、安装命令统一、规则文案与真实能力对齐。

同时补三平台 CI，明确许可证，整理可公开回放的脱敏实测案例。先把“正确安装、错误被可靠识别”做好。

验收：人读/JSON 输出具有一致的成功失败语义；官方固定版本样例能导入并保留未决信息；新环境能从 README 走到 init 和首次验收。许可证类型需要维护者选择。

### 第二阶段：以真实项目为载体补最小变更追踪

建议围绕以下结果设计 v0.2，具体命令名可再定：

1. 读取 Git 基线与当前差异，识别变更的条目；删除条目时也能利用旧图计算影响。
2. 增加最小来源及代码/测试文件映射，输出文件路径与证据。
3. 对每个候选记录“已修改 / 已检查无需修改 / 尚未确认”，不允许无解释地消失。
4. 保护 PASS_TO_PASS 基线，对断言删除、测试削弱、越界改动提供可审查的差异。
5. 统一输出覆盖情况、未解决冲突、测试结果与整体结论，区分“通过”和“证据不足”。

不需要先实现通用调用图、多代理审核系统或语义检索平台。先覆盖一个真实仓库的关键工作流，并在 specripple 自身迭代中使用它。

### 第三阶段：验证增量收益，再决定扩展

建议选两个持续开发的真实项目，准备约 20 个有人工预期结果的变更，包括参数变化、缺链接、删除/拆分、代码先改、冲突裁决、无需传播的局部调整与保留集回归。

固定宿主、模型、初始仓库和用户请求，对照三种配置：宿主加普通同步提示、宿主加流程技能、宿主加技能与完整 CLI。可对关键场景重复 3 次观察稳定性。预期影响与关键验收由独立于执行 Agent 的人工评审或冻结测试确定，不能只让执行者评价自己。

记录漏改、无关修改、错误通过、误报、人工纠正次数、耗时与 token。原计划记录的 43k/52.7k token 只是单次演示的成本线索，没有对照，不能据此断言节省或浪费。

如果 CLI 相比仅技能没有明显减少遗漏或人工审查负担，应缩小为技能包加检查器；如果收益成立，再加 MCP、检索通道和更多宿主。MCP 改善接入，不能直接提高影响分析的正确性。
