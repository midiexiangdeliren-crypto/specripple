## 二、条目 schema v0（一切的地基）

每个条目一个 markdown 文件，YAML frontmatter + 正文：

```yaml
---
id: REQ-012              # 全仓唯一，{REQ|TASK|PLAN|CON|RAT}-三位数字
type: req                # req | task | con | rationale（plan 与 spec 同构，v0 并入 req）
title: 手机号验证码登录
status: active           # draft → active → done；active/deprecated 可置废
depends_on: [REQ-010]    # 上游依赖
links:                   # 结构化链接
  - {to: TASK-003, kind: realized-by, src: manual}   # kind: realized-by | refines | verifies | clarifies
---
正文：EARS 句式描述 + "## Acceptance" 块内 Given/When/Then 列表
```

规则：id 不可变；正文用 UTF-8；artifacts/ 由 git 管理。index.json 为可重建派生物（全部条目的 id、title、status、依赖与链接邻接表、每条约 100 字符摘要）。

## 三、四个命令的规格与验收

**align index**：扫描 artifacts/**/*.md → 解析校验 → 重建 index.json。验收：demo-project 100% 条目化；重复 id、字段非法时以非零退出码报错并指明文件；两次重建的 index.json 字节级一致（确定性）。

**align impact <ID>**：从该条目沿 depends_on 与 links 做有向闭包（BFS），输出影响集。人读格式默认，--json 输出机器格式：每项含 id、文件路径、到达路径（证据链，如 REQ-012 --realized-by--> TASK-003）、深度。验收：demo-project 中手工核对影响集完全一致；对不存在 id 报错。

**align detect**：规则层，零 token，输出 CRITICAL/HIGH/MEDIUM/LOW 分级报告（--json 同样支持）。v0 六条规则：D1 引用完整性（depends_on/links 指向不存在的 id）——CRITICAL；D2 重复 id——CRITICAL；D3 状态机违规（如依赖方已 done 而被依赖方重新置 active 却未重开依赖方）——HIGH；D4 结构违规（status=active 的 req 缺 Acceptance 块或缺 EARS 句式）——MEDIUM；D5 未决残留（TODO / [NEEDS CLARIFICATION] / pending_clarification 状态存在）——HIGH；D6 术语未定义（glossary.md 存在时才启用，正文加粗术语不在词表）——LOW。验收：每条规则至少一正一反两个测试用例；空仓库不误报。

**align verify**：读 assertions.yaml（fail_to_pass 与 pass_to_pass 两组），v0 检查器四种：file_exists、file_contains、file_not_contains、regex_match，逐条执行输出报告，任何 fail_to_pass 未通过或 pass_to_pass 被破坏都以非零退出。验收：demo-project 故意破坏一条断言能变红，修复后变绿。

## 四、demo-project 与 demo 命令

demo-project 为内置示例（随包分发）：5 个 REQ、4 个 TASK、1 个 constitution、1 个含两词条的 glossary；故意埋三类问题——一条悬空链接（触发 D1）、一处 TODO 残留（触发 D5）、一条依赖链 REQ→REQ→TASK（供 impact 演示）。`uvx align demo`：把示例复制到临时目录，依次运行 index/impact/detect/verify 并彩色输出——这是开源冷启动的 60 秒体验，也是所有验收的载体。

## 五、MVP-2：宿主接入（D8—D12）

技能三份（SKILL.md，description 只写触发条件与症状，不概述流程——superpowers 纪律）：aligning-changes（主流程：影响→路由→编辑→检出→消解→复检，含"完成前证据先于宣告"）、detecting-conflicts（六类检查检查单，LLM 层）、resolving-conflicts（一次一题、2—4 选项附推荐、结论写回并落 rationale 条目）。init.py：`align-kit init --host codex|claude [--remove] [--dry-run]`——AGENTS.md 写入带版本戳标记块（幂等可摘除），复制技能到 .agents/skills/ 与 .claude/skills/ 薄壳，Claude Code 另生成 .claude/commands/align.md。import-speckit：把 Spec Kit 产物（spec/plan/tasks/constitution）转换为条目仓库，锁定官方模板版本并做黄金快照测试。

Codex 实测清单（D11）：改 demo-project 的一个 REQ → agent 自主调用 impact → 编辑受影响条目与代码 → 对埋设冲突发起消解提问 → verify 全绿收尾。沙箱写权限审批的引导写进技能正文。Claude Code（D12）同清单复跑。DSH（D13）：npx 启动极简模式，验证技能包与 MCP 桥各一步；不通即降级为"OpenAI 兼容模型 + MCP"接入并记录，不恋战。

## 六、开发纪律与风险

每命令先写失败测试再实现；小步提交；全仓 UTF-8（已知 Windows 编码坑按既有清单规避）；提交信息英文。风险与预案：spec-kit 模板变动（锁版本 + 快照测试，变动时只修转换器）；Codex 沙箱阻断 align 写文件（技能中写明批准引导，实测阶段解决）；DSH 文档不足（限半天调研盒，超时降级）；进度超支（MVP-1 为承诺底线，其后顺延）。
