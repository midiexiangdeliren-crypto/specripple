# 路线图

更新日期：2026-09-20。带优先级与触发条件；已完成项移入 `docs/development-plan.md`，历史设想见归档目录。

## 方向声明

specripple 的差异点不是"有变更闭环"（Spec Kit 的 Living/Flow-Back Spec 与 OpenSpec 都已具备），而是：**同一模型、同一任务下，是否减少漏改、说明影响依据、并对错误完成给出更可靠的阻断。** 路线图围绕这个可验证命题排布；不能支撑该命题的能力（更大的平台、更多检索通道）一律后置。

## 收益验证实验（扩张的门槛）

三配置对照（普通同步提示 / 流程技能 / 技能 + 完整 CLI）× 约 20 个有人工预期的变更 × 关键场景重复。指标：漏改数、无关修改数、错误通过数、误报数、人工纠正次数、耗时、token。判定：CLI 相比仅技能无显著减漏改 → 收缩为技能包 + 检查器；收益成立 → 才启动下表后置项。

## 后置池（按触发条件启动）

| 项 | 触发条件 |
| --- | --- |
| MCP server（FastMCP：impact/detect/verify 三工具） | 收益验证成立；或 ≥2 家宿主出现结构化调用需求。MCP 改善接入体验，不提高影响分析正确性 |
| BM25 + RRF 检索通道（补缺链候选） | 三态记录显示"缺链候选"是漏改主因时优先；先于向量方案 |
| CRR / 对齐质量报表 | 论文实验阶段需要批量指标时 |
| Claude Code 真机实测 | 维护者恢复该决策时（D12 遗留） |
| 多 feature / 共享 constitution 布局的 Spec Kit 导入、来源映射、重新导入 | 出现真实多 feature 用户时 |
| Codex 沙箱注记之外的其他宿主薄壳（Copilot/Cursor 专有文件） | 对应宿主出现真实使用者 |

## 明确不做

Web UI；自研 LLM 编排（宿主承担）；PyPI 发布（维护者决策，git 直装）；把"所有工件自动保持一致"作为产品承诺——输出的是有依据的候选集与可执行验收，判断留给人。
